# Milestone 2.5: SSH keys

RemoteDock generates Ed25519 keys by default and RSA 4096 for compatibility. Imported files must use OpenSSH private-key encoding and contain Ed25519 or RSA with at least 2048 bits. DSA, ECDSA, hardware-backed keys, PEM and PKCS#8 are outside this milestone. Unsupported/corrupt files produce a structured error. Encrypted imports require a correct passphrase; duplicate public identities are rejected even if filenames, encryption or comments differ.

## Local storage and threat model

Generation and parsing use the existing Rust `ssh-key` library, OS cryptographic randomness and its OpenSSH encryption support (bcrypt KDF and the library's OpenSSH cipher). RSA size is explicitly set to 4096. No JavaScript generation, subprocess generation, custom crypto or insecure fallback is used. The installed ssh-key 0.6.7 RSA signing adapter duplicates prime p when converting to RustCrypto; RemoteDock bypasses that adapter and supplies n, e, d, p and q directly to the maintained RustCrypto rsa library for validation and a signing/verification proof. Ed25519 uses ssh-key for the proof. OpenSSH serialization/encryption remains in ssh-key, and SSH authentication remains in libssh2. Import preserves the original file; managed copies are reserialized and encrypted when a passphrase is supplied.

Managed private files live in `app_data_dir()/ssh-keys/<UUID>`. The directory is mode 0700 and files are 0600 on macOS. Encrypted output uses a same-directory 0600 staging file and atomic no-clobber persistence. Without a passphrase, the final UUID file is intentionally unencrypted and written exclusively with 0600 permissions, then synced before the SQLite record is published atomically. This avoids a plaintext temporary file. Application readers cannot discover a partial file through the repository; an external filesystem reader could observe the final UUID file during this initial write. A crash before registration leaves a cleanup intent. Existing files are never overwritten. Public keys live in SQLite; no separate managed `.pub` file is needed. Public export writes a user-selected new `.pub` file and refuses overwriting an existing file.

Permissions protect against other local accounts, not malware running as the logged-in user, administrator access, unlocked backups or a compromised webview. Use a passphrase and FileVault for stronger at-rest protection. OS Keychain holds only explicitly saved passphrases, with references owned by reusable key ID. Keychain refusal fails closed. An external file must be readable, bounded in size and have no group/other permissions; RemoteDock does not change its permissions. External key identity is rechecked before authentication; replacement with different material requires an explicit new import and assignment.

Private contents are never IPC responses or logs. Password fields are uncontrolled inputs, cleared upon submission, and secrets bypass React/Zustand state and TanStack mutation variables/caches. Secrets briefly exist in webview input/local call memory and local IPC; JavaScript garbage collection cannot promise erasure. Rust input and encoded secret buffers use zeroizing storage. Unsaved connection passphrases use the existing per-server leased runtime and expire with it; import/generation passphrases are dropped after the operation. Public-key copying copies only public material.

## Persistence, ownership and compatibility

Migration 004 adds reusable key metadata, unique SHA-256 identities and a nullable server foreign key with restricted deletion. The application service coordinates repository, credential and file interfaces. SQL remains in the SQLite adapter. Assignments and server form changes use transactional persistence. Assignment invalidates the existing session, transient passphrase and pending host observations while preserving trusted remote host identity. Deleting a server never deletes a shared key or its Keychain item.

Legacy path-based server credentials remain intact and are used only without an assigned key. Import the legacy file explicitly, then select the imported record to migrate. Unassigning a reusable key restores the retained legacy setting; it does not select a different reusable key. Client authentication keys and server host trust remain independent.

Assigned keys cannot be deleted. Every removal requires confirmation; managed file deletion requires a separate checkbox, off by default. External files are always retained. Retaining a managed file removes its record but leaves the UUID file in the managed directory; back up or remove that file manually when no longer needed.

Before filesystem/Keychain creation, a cleanup intent is committed. Insertion of metadata and removal of the intent are atomic. Deletion queues cleanup and deletes metadata in one transaction; a foreign-key race rolls back both. Cleanup is idempotent and retried at startup. Failed cleanup leaves a durable intent and reports an error; the record may already be removed. If startup cleanup is blocked by Keychain, unlock/allow Keychain and restart. Files with no committed record following an interrupted creation are removed, never silently adopted. Cleanup paths must be direct children of the managed directory. A crash may leave an unnamed staging file; it is not automatically adopted or deleted and can be manually removed after inspection. File/SQLite/Keychain operations are not a single cross-resource transaction.

## Verification and manual acceptance

Run the normal frontend and Rust checks in README. Unit tests cover generation, encryption, identity, imports, storage, permissions, assignments, preservation of trust, deletion restrictions, transactional server saving and retryable cleanup. UI tests cover transient secret submission, selection and confirmed deletion.

For real authentication, start the disposable loopback fixture described in [Milestone 2 testing](milestone-2-testing.md). Its start script now generates additional disposable Ed25519 and encrypted RSA 4096 credentials using the application's Rust codec. The ignored integration suite authenticates with both generated files and reimported temporary copies. It never uses production credentials. Docker must already be running; default `cargo test` reports these tests as ignored.

On macOS, manually verify native picker cancellation, encrypted import retry, explicit Keychain opt-in and refusal, restart/unlock, native export and existing-file refusal, clipboard access, keyboard navigation, two servers sharing a key, blocked deletion, selection changes, and unknown/changed remote host trust. No VPS provisioning or remote configuration is performed by this milestone.
